## Context

当前 FastAPI 应用使用 SQLAlchemy 模型同时保存岗位、批次、简历元数据和评分结果；前端通过岗位、批次和结果 API 轮询。`AgentScopeProvider` 已使用 `OpenAIChatModel`、`OpenAICredential` 和可配置的 `openai_base_url`，因此百炼可以复用现有适配层。项目面向少量本地用户，已明确不需要分析历史或重启恢复。

## Goals / Non-Goals

### Goals

- 用单个后端 JSON 文件持久保存岗位规则，并保留现有岗位 CRUD API。
- 用进程内内存承载一次分析的批次、解析文本、状态、评分和证据。
- 在不新增供应商 SDK 的前提下，通过 AgentScope 的 OpenAI 兼容路径接入百炼。
- 保留结构化评分、敏感特征约束、单文件失败隔离和现有前端响应形状。
- 明确单 worker、重启丢失分析状态和外部传输简历文本的边界。

### Non-Goals

- 不提供跨进程、跨实例或服务重启后的分析恢复。
- 不实现历史候选人档案、审计报表、导出或多租户权限。
- 不把岗位规则写入 `frontend/public`，不把 API Key 放入浏览器。
- 不在本次变更中增加 Redis、队列服务或复杂冲突解决界面。

## Decisions

### 1. 后端 JSON 文件作为唯一持久化数据源

选择 `backend/data/roles.json` 而不是前端 `public` 或 localStorage。后端文件可以被 CRUD API 直接读取和写入，且不会被浏览器公开；JSON 与现有 API 数据结构一致，依赖和部署复杂度最低。文件内容使用版本化顶层对象（例如 `version` 与 `roles`），角色和要求使用稳定 UUID，缺失文件初始化为空集合。

每次变更在进程内锁和跨进程文件锁保护下读取最新内容、校验、写入临时文件，再通过原子替换完成保存。当前规模不引入复杂乐观锁 UI；同一时间的写入按顺序执行，冲突时以后到的有效写入为准，并保留统一的 409/配置错误响应约定。

替代方案：SQLite 能更可靠地处理并发，但与“去掉数据库”的目标冲突；localStorage 只在单个浏览器可见，无法成为后端评估的权威规则源；`frontend/public` 在构建和部署后通常不可写且会暴露数据。

### 2. 进程内内存存储一次分析

用一个进程级 store 按 `batch_id` 保存批次、文件状态、临时文本、岗位快照和评估结果。上传、批次查询、结果查询和后台评估继续沿用现有 API 语义，开始评估时复制岗位规则快照，避免岗位文件后续编辑影响当前任务。终态数据通过惰性 TTL 清理，不再写入数据库。

替代方案：把评估改成同步请求会让上传请求受模型延迟和超时影响；Redis 能支持多 worker 但对两三名本地用户过重；继续使用 SQLite 最稳但保留了用户明确希望移除的持久化层。

### 3. 复用 AgentScope 的 OpenAI 兼容适配器

继续使用当前 `AgentScopeProvider` 的模型和凭据抽象，将百炼的 API Key、模型名和地域/业务空间 Base URL 映射到现有环境变量。默认不增加 DashScope SDK，避免同时维护两套调用路径。先尝试 AgentScope 的结构化输出能力；若目标模型或兼容接口不能直接完成 schema 输出，则使用 JSON Object 提示、解析和 `EvaluationResult` Pydantic 校验作为兼容回退。应用始终自己计算通过与否，不接受模型直接给出的资格布尔值作为最终真相。

替代方案：直接使用 DashScope 原生 SDK 可能获得更多供应商特性，但会引入新依赖和另一套错误/响应模型；单独写 HTTP 客户端会重复已有 AgentScope 能力。

### 4. 保留 API 合同，替换后端存储实现

尽量保持前端使用的 `/api/roles`、`/api/batches` 和 `/api/batches/{id}/results` 响应结构，减少 UI 改动。数据库模型、依赖、Alembic 配置和相关 session 代码移除后，由内存对象和 JSON 文件仓储提供同样的字段。当前工作区数据库表均无数据，因此不安排历史数据迁移；若部署环境已有岗位数据，应在切换前手动导出为 JSON。

### 5. 通过配置和测试控制运行边界

为内存 TTL、角色文件路径、AI provider、模型和 Base URL 提供后端环境变量；启动文档明确使用单 worker，开发 `--reload` 会清空当前分析。测试覆盖 JSON 文件 CRUD/损坏恢复、内存生命周期、单 worker 约束、模拟百炼结构化成功/失败以及 API Key/简历文本不进入日志。真实百炼冒烟测试仅在显式提供环境变量时运行，不让离线测试依赖外部网络。

## Risks / Trade-offs

- [重启丢失活动分析] → 在界面和 README 中明确一次性分析语义；仅岗位 JSON 跨重启保留。
- [多用户同时编辑产生最后写入覆盖] → 使用锁、原子替换并在同一写锁内读取最新内容；接受小规模本地工具的最后写入策略。
- [角色 JSON 损坏导致服务不可用] → 启动和写入前严格校验，保留最近一次备份或临时文件，并拒绝用空集合静默覆盖坏文件。
- [百炼兼容接口的结构化输出差异] → 使用真实模型冒烟测试，保留 JSON Object + Pydantic 校验回退并隔离单文件失败。
- [简历文本发送到外部服务] → API Key 只在后端环境变量中读取，禁写日志，界面/文档明确外部处理范围。
- [移除数据库扩大改造面] → 保持前端 API 形状，先替换仓储和测试，再删除 SQLAlchemy/Alembic 依赖与配置。

## Migration Plan

1. 增加并校验 `backend/data/roles.json`，必要时从现有数据库手动导出岗位规则；本工作区当前数据库为空，可直接初始化空集合。
2. 先实现 JSON 角色仓储和内存分析 store，使用 API 回归测试替换数据库夹具。
3. 将批次、文件和评分流程切换到内存对象，保留解析文本终态清理和角色快照。
4. 在模拟 provider 测试通过后配置百炼环境变量，运行一次显式的真实模型结构化输出冒烟测试。
5. 删除 SQLAlchemy/Alembic 运行依赖、数据库配置和遗留数据库初始化路径，更新 README 与启动命令为单 worker。
6. 若需要回滚，在同一发布版本恢复数据库依赖和旧仓储代码；JSON 岗位文件可作为人工导入源，内存分析结果不做迁移。
