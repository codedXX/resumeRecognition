## Context

当前工作台已有顶部 `notice` 状态文本和基于 Radix Dialog 的岗位编辑弹窗，但上传 mutation 将“HTTP 成功”误当成“所有文件成功”，且禁用的开始按钮无法接收点击事件。后端仍会对每个文件返回状态和错误，因此前端可以在不改变 API 合同的前提下补全反馈链路。

## Goals / Non-Goals

**Goals:**

- 让用户在文件超限、格式不支持、解析失败或批量部分失败时立即知道具体文件和处理方式。
- 让开始评估按钮附近始终解释不可用原因，并在缺少岗位时突出岗位选择入口。
- 统一成功、警告、错误反馈的视觉级别、自动聚焦和无障碍语义。
- 通过前端单元测试锁定所有关键状态文案和弹窗行为。

**Non-Goals:**

- 不改变后端上传上限、文件解析规则、评估 API 或批次状态合同。
- 不把客户端校验当作安全边界；服务端仍负责最终校验。
- 不引入新的 UI 框架、全局状态库或持久化通知中心。

## Decisions

### 1. 服务端结果为准，客户端提前校验为体验优化

上传处理同时保留客户端大小/扩展名预检和服务端逐文件状态解析。预检可避免明显超限文件发送网络请求；服务端返回的 `failed`/`unreadable` 文件仍必须再次汇总，防止绕过客户端时静默失败。上限常量从现有 10 MiB 配置同步，若未来后端上限可动态变化，服务端提示优先。

### 2. 复用 Radix Dialog 展示可行动错误

新增一个轻量上传反馈对话框，列出失败文件、原因和下一步（重新选择或关闭）；成功文件数量与可继续操作在对话框中同时呈现。短暂成功消息继续使用 `role="status"`，错误/警告对话框使用 `role="alertdialog"` 并提供明确标题，避免仅依赖颜色。

### 3. 用状态驱动的启动引导替代“灰色按钮猜谜”

保留按钮禁用以阻止非法请求，但在按钮上方或下方显示动态 checklist 文案：缺岗位时说明“请选择岗位”，缺可读文件时说明“请上传可读取的 PDF 或 DOCX”，过期时说明重新上传。岗位缺失时给岗位选择器增加警示样式，并在上传完成后将焦点移到该控件（若用户尚未选择岗位）。

### 4. 将 mutation 成功与业务成功分离

上传 mutation 的成功回调先检查响应文件状态：全部就绪才显示成功引导；存在失败项则显示警告/错误对话框，不再覆盖失败原因。评估 mutation 的网络错误和后端失败继续使用错误级别反馈，并保留候选人行内错误详情。

## Risks / Trade-offs

- [客户端上限与后端环境变量不一致] → 客户端预检只作为提前提示，服务端返回仍覆盖最终结果，并在文案中使用“当前服务限制”。
- [弹窗过多打断批量操作] → 仅在存在失败项或需要用户采取行动时弹出；纯成功和等待状态使用非阻塞提示。
- [自定义 Select 聚焦支持不足] → 为选择器触发按钮补充可转发 ref 或使用等效 `aria-describedby`/高亮引导，不改变其键盘交互合同。
- [错误提示包含过长文件名] → 对话框中允许换行并限制列表高度，保留完整文本供辅助技术读取。

## Migration Plan

1. 增加前端反馈状态模型、上传结果分类和弹窗/引导组件样式。
2. 接入上传预检与逐文件结果汇总，补充岗位缺失和无可读文件的动态引导。
3. 增加前端交互测试，运行 `npm test` 和 `npm run build`。
4. 手工验证超限文件、混合批次、未选岗位、过期批次和评估服务错误；若回滚，只需恢复前端组件，后端无需迁移。
